面试满分的那套缓存方案，让我赔过三万七。

先更库、再删缓存、500 毫秒延迟双删兜底——每一步都背得滚瓜烂熟，线上照样出事。

2021 年双十一前一周，凌晨两点十七分，我蹲在公司二十层的消防通道里接客服电话。

用户的原话我记到现在：商品页显示有货，付款成功，然后提示库存不足。

一个用户也就算了。那晚一共九个。

我们做的是品牌特卖，库存就是命根子。Redis 集群三十二个节点，缓存了四十万个 SKU，大促峰值 QPS 八千。这套缓存是我半年前亲自设计的，写接口统一走「更新数据库 → 删除缓存 → 500 毫秒后延迟再删一次」。

当时我觉得自己特别规范。

## 那天晚上到底出了什么事

我盯着监控，看了三个小时，一直以为是缓存雪崩。

后来是消息积压的曲线把我看醒的。

延迟双删的第二次删除，我走的是消息队列。那晚 MQ 有两个消费者卡在 GC 上，删除消息积压了三千多条。

库存的脏数据在缓存里躺了四十一分钟。

凌晨三点半，我在运营群里说了一句「先把这个 SKU 下架」，然后被大促负责人电话叫醒的时候，已经是四点半了。

那天上午我们补了九个用户的差价，加上后续的客诉和赔付，一共三万七千二。

四十一分钟，够用户把一个已经卖光的尺码下单十几次。

这不是 Redis 的锅。是我把「一致性」这件事，做成了一个藏在业务代码里的 sleep。

## 标准答案里唯一没毛病的那半句

说句公道话，「先更新数据库、再删缓存」这个顺序是对的。

反过来做，先删缓存再更库，中间那段空窗期会把旧值重新读回缓存，还会一直躺到过期。这个坑我在更早的一个项目踩过，那会儿连双删都不知道，脏数据在里面躺了两天。

所以顺序没错，错在后面那半句：延迟双删、删两次、兜底。

面试答案把「不一致」当成一次操作里的时序问题，删两次就抹平了。可生产环境里的不一致，来源根本不是时序。

是主从复制的延迟，是消息中间件的积压，是消费者重启，是某台机器的时钟漂移，是你半夜三点被人叫醒时脑子转不动的那个瞬间。

## 延迟双删最要命的地方：那个延迟是拍脑袋的

500 毫秒？1 秒？2 秒？

我面试过十几个候选人，问到这个点，四个人说 500 毫秒。我再问为什么是 500，答案很统一：网上都这么写。

这就是问题所在。一个需要靠随机数决定正确性的方案，凭什么叫方案？

更难受的是它假设了一件事：延迟期间不会再有读请求把旧值写回去。

但真的会。你第一次删完，主从还没同步，一个读请求打到从库，拿到旧库存，顺手写回了缓存。你 500 毫秒后删第二次，第三个读请求又赶在前面回填。

删除和回填不是原子的。你以为在修时序，其实在赌运气。

主从延迟在大促当晚可以是 30 毫秒，也可以是 3 秒。你的延迟是固定的，延迟本身是浮动的。

这么算，赢面在谁那边？

## 换个问法，方案就出来了

后来复盘，我承认自己犯的是最典型的一种错：上来就选技术方案，从来没问过业务一句话。

这句话是：**这份数据，你能容忍脏几秒？**

商品标题写错了，脏五分钟没人报警。库存数字，脏一秒钟就是赔钱。优惠券金额，脏一秒钟可能就是一晚上的资损。

数据能容忍的时长不一样，方案就不该一样。

我们后来把商品中心的数据拆成三类，处置方式完全不同。

**第一类，能忍几分钟的。** 别在业务代码里删缓存了，订阅 binlog 异步删。我们上了 Canal，删除失败进死信队列，积压超过阈值直接打值班手机。

好处很朴素：能重试，能监控，出事能补删。大促那天如果我有这个，四十一分钟会变成四十一秒。

**第二类，一秒钟都不能脏的。** 别让缓存参与判断。

库存扣减放在数据库里做条件更新：`update stock set num = num - 1 where id = ? and num >= 1`，看影响行数。缓存只负责展示，展示层就算旧了三秒，用户点下单的时候数据库还会拦一次。

真正的判断不在缓存上，缓存脏不脏就不重要了。

**第三类，既要用缓存判断、又不能脏的。** 比如秒杀资格。这种场景别指望删除成功，给数据加版本号。

写入时 version 加一，读缓存的时候顺手比对一下数据库版本，对不上就回源或者直接拒绝。

```sql
update coupon set status = 1, version = version + 1
where id = ? and status = 0 and version = ?;
```

校验永远比祈祷删除成功可靠。

## 但 binlog 也不是银弹

用了 Canal 之后我踏实了半年，然后被现实教育了第二次。

有一回 Kafka 集群做了次迁移，binlog 的 topic 少了一个分区，那天的商品价格改了一百多个 SKU，缓存全没更新。

用户看到的价格是旧的，下单的时候才被拦。投诉电话照旧。

binlog 方案解决的是「删除动作能不能重试」，解决不了「链路断了怎么办」。

后来我们加了两件事：一个是缓存里存数据的最后更新时间，读的时候跟数据库比一下，超过十分钟就强制回源；一个是每天凌晨跑一遍对账脚本，把关键表的修改时间和缓存里的时间戳对一遍，不一致的补删。

多花了不到两百行代码，从此这类问题不用再靠人半夜爬起来查。

## 我为这个答案付过的另一笔学费

还有一个更蠢的错误，我到现在都不太愿意提。

那阵子我特别迷延迟双删，给商品中心两百多个写接口统一加了注解，统一睡 500 毫秒。

大促当天，这些 sleep 吃掉了 Tomcat 线程池三成的容量。接口 P99 从 80 毫秒涨到 700 毫秒，运维在群里问是不是有人压测。

为了防止一个概率极低的脏读，我把整个系统的吞吐砍了一半。

这是我职业生涯里性价比最低的一次优化，没有之一。

## 我给团队定的规矩

现在带人，我就定三条，很土但管用。

缓存删除的代码，必须能回答「失败了谁来兜」，答不出来就没资格 merge。

睡在业务代码里的线程，一律当 bug 处理。要延迟就交给调度器，别占着 Tomcat 的线程打呼噜。

资金、库存、名额这三种数据，写操作必须在数据库里带上条件，缓存永远不许作为扣减和判断的唯一依据。

这三条没有一个字提到 Redis。因为缓存一致性从来不是 Redis 的问题，是你对业务容忍度的定义问题。

## 为什么大家还在背延迟双删

因为面试需要一个能背下来的答案。

面试官想确认的是「你知不知道并发下缓存会脏」，不是「你会不会给数据定一致性预算」。前者一句话能问完，后者要聊二十分钟。

于是延迟双删成了行业里的标准咒语。背得出的人多，说得清为什么是 500 毫秒的人少。

我现在的做法很简单：新系统里，任何写缓存的代码都必须能回答三个问题——这份数据能脏多久，删除失败了谁来兜，积压了我从哪里看。

答不上来，就别写 delete。

## 最后一句

下次再有人问你缓存一致性，先反问他一句：这份数据你能容忍脏几秒？

答得出来的人，方案自己会长出来。答不出来的人，背延迟双删也救不了那四十一分钟。
